# VCS Contract — Perforce (p4)

Implementation of the [VCS contract](README.md) for Perforce. Loaded when `integration.json → vcs.type == "p4"`. If
you know git but not Perforce, the key shifts are: a workspace is **read-only by default**, and work is submitted in
changelists to a central server rather than committed locally.

State recorded in `integration.json → vcs.p4` (the stream, or the changelist number, also goes in the top-level
`branch`):

```json
"p4": {
  "port": null,
  "client": "<workspace name — verified, not created>",
  "stream": "//depot/<game>-ludeo",
  "depotPath": "//depot/<game>/...",
  "mcp": "perforce",
  "changelist": null
}
```

`port: null` inherits `P4PORT` from the environment or `P4CONFIG`; `stream: null` for a classic depot; `mcp` is the
connected Perforce MCP server's name, or `null` for the CLI fallback.

## How p4 operations run

1. **Primary — a Perforce MCP server.** If one is connected (the official Perforce P4 MCP is recommended), use its
   tools for `edit` / `add` / `shelve` / `submit` and stream operations.
2. **Fallback — the `p4` CLI.** Every operation below shows the CLI form.
3. **Don't make the client `allwrite`** as a shortcut — it loses Perforce's clobber protection. Open files for edit.

First verify the workspace is synced and logged in (`p4 info`, `p4 login -s`). The skill verifies the client; it does
not create one.

## ⚠ `ensure_editable(path)` — before EVERY write

Every tracked file is read-only until opened, and the agent's write tools fail on it. Before any write to a workspace
file:

- **Existing file:** the MCP `edit` tool, or `p4 edit -c <CL> "<path>"`.
- **New file:** the MCP `add` tool, or `p4 add -c <CL> "<path>"`.

This holds for the **whole** integration — game code, build files, `ludeo.ini`, `ludeo-integration-plan/` and the state
file included.

## `create_isolation(name)`

Find whether the depot is stream-based, then propose the matching isolation and **let the user confirm** — never create
or switch streams unprompted:

```bash
p4 -ztag -F %Stream% client -o    # non-empty => the client is bound to a stream
```

- **Stream depot** — propose a task or development stream off the current one (`//<depot>/<game>-ludeo`, or the
  studio's convention), and ask whether to create and switch to it or let them do it per their stream policy. If asked
  to proceed:
  ```bash
  p4 stream -t development -P <current-stream> //<depot>/<game>-ludeo
  p4 client -s -S //<depot>/<game>-ludeo
  p4 sync
  ```
- **Classic depot** — no branch to switch to: keep all integration work in a **dedicated pending changelist** and ask
  the user to confirm:
  ```bash
  p4 --field "Description=Ludeo integration — <game>" change -o | p4 change -i   # prints "Change N created"
  ```
  Record the number in `vcs.p4.changelist`; every `edit` / `add` uses `-c <CL>`.

## `acquire_component(dest)`

No submodules — copy the release (`../1-build-game-with-sdk.md` Step 2) into `external/ludeo/LudeoCoreSDK_<version>/`,
then `add` the tree (MCP `add`, or `p4 add -c <CL> "external/ludeo/..."`). Check the binaries landed whole (> 1 MB, not
LFS pointer files). The SDK's `Bin/`, `Lib/` and `ThirdParty/` are build inputs and must be added; respect `.p4ignore`
for the game's own build output. If the studio already vendored the SDK into the depot, confirm the path and version.

## `checkpoint(summary)` and the `reconcile` safety net

A write that skipped `ensure_editable` leaves a file out of the changelist silently. At each `checkpoint`, preview, then
reconcile the integration's paths — **ask the user first**, since reconcile opens files:

```bash
p4 status                                                      # read-only preview
p4 reconcile -c <CL> -aed "<project>/<integration paths>"      # scope to the integration's paths, never the workspace
```

Report what it opened. Per-phase policy on a stream: `p4 submit -c <CL>` to the integration stream, with the user's
go-ahead. On a classic depot, never submit to the mainline — the pending changelist **is** the isolation; shelve it
(`p4 shelve -c <CL>`) so the work is backed up on the server.

## `open_review(summary)`

Only when the user asks, after the build gate passes. Shelve the work changelist (MCP `shelve`, or `p4 shelve -c <CL>`),
then create a Swarm review from it — the official MCP can drive Swarm; otherwise give the user the CL number. Submit
only on the user's approval.

## `guard_destructive`

Never run an irreversible p4 command on a single failed check — confirm with two independent checks (absolute paths)
first. Never run these speculatively:

`p4 revert` (discards the checkout) · `p4 sync -f` (overwrites local files) · `p4 client -d` · `p4 obliterate`

**You are online:** most operations talk to the server, and a `submit` is immediately visible to everyone. Keep the
work in the pending changelist or the integration stream until review.
